## Процесс проектирования

**Компоненты вперёд требований.** Схема из квадратов рисуется до разговора о том, что система должна делать и по каким числам это проверяется. Дизайн выглядит убедительно и не проверяем. → Сначала [W0](00-workflow.md#w0) и [W1](00-workflow.md#w1), потом схема.

**Нефункциональные требования без чисел.** «Быстро, надёжно, масштабируемо» не позволяет принять ни одного решения и не позволяет узнать, достигнута ли цель. → Число и способ измерения на каждое требование.

**Оценка по среднему.** Ёмкость посчитана по среднему трафику, система живёт в пике. → Коэффициент пика 3–10, для событийных нагрузок больше.

**Решение из чужого блога.** Архитектура компании с другими числами перенесена целиком. Инженерные блоги описывают итог, а не путь, и молчат о промежуточных решениях, работавших годами. → Сначала контекст и ограничения, потом решение ([T-151](topics/12-case-studies.md#real-architectures)).

**Отсутствие «вне рамок».** Список исключений не зафиксирован, объём растёт молча. → Явный список того, чего не делаем.

<a id="api"></a>

## API и контракты

**`200 OK` с ошибкой в теле.** Ломает всё, что между клиентом и сервером: балансировщик считает ответ успешным, кэш кэширует, мониторинг зелёный, клиент не повторяет. → Осмысленные коды ([T-005](topics/01-network-and-api.md#http-status)).

**Неидемпотентная небезопасная операция.** Клиент получил таймаут и не знает, выполнилась ли операция. Любой повтор — риск двойного эффекта. → Ключ идемпотентности ([T-016](topics/01-network-and-api.md#idempotency)).

**API от таблиц БД.** Схема хранения протекает в публичный контракт, миграция становится ломающим изменением. → Контракт от сценариев использования.

**Пагинация по offset на растущей коллекции.** Задержка растёт с номером страницы, вставки сдвигают выдачу, пользователь видит дубли и пропуски. → Курсорная пагинация ([T-014](topics/01-network-and-api.md#pagination)).

**Клиент падает на неизвестном поле.** Добавить поле в ответ становится ломающим изменением, эволюция API останавливается. → Игнорировать неизвестные поля — правило с первого дня ([T-017](topics/01-network-and-api.md#versioning)).

**Сериализация доменной модели в ответ.** Внутренние поля утекают наружу, а переименование поля ломает клиентов. → Явное преобразование в ответ ([T-105](topics/09-security.md#api-security)).

**Массовый эндпоинт без ограничения размера.** Один запрос исчерпывает память сервиса. → Лимиты по числу элементов и объёму тела ([T-015](topics/01-network-and-api.md#bulk)).

<a id="data"></a>

## Данные

**Выбор БД до формулировки паттернов доступа.** Хранилище выбрано по привычке, а нужный запрос оказывается невыразимым или неприемлемо медленным. → Список запросов с частотой и требованиями, потом выбор ([T-033](topics/03-storage-and-data.md#data-modeling)).

**«Транзакция есть — значит гонок нет».** Уровень изоляции по умолчанию допускает потерянные обновления и write skew. Баги тихие и воспроизводятся раз в тысячу операций. → Разобрать конкретные аномалии ([T-038](topics/03-storage-and-data.md#isolation)).

**Индексы «на всякий случай».** Каждый индекс — дополнительная запись при каждом изменении; замедление записи объясняют «ростом нагрузки». → Индекс под конкретный частый и селективный запрос ([T-035](topics/03-storage-and-data.md#indexes)).

**Ключ шардирования, выбранный до понимания запросов.** Запросы без этого ключа превращаются в обход всех шардов; переиграть почти невозможно. → Ключ выводится из паттернов доступа ([T-040](topics/03-storage-and-data.md#sharding)).

**Раннее шардирование.** Сложность распределённых данных получена до того, как исчерпаны вертикальный рост, кэш, реплики и асинхронность. → Порядок из [W5](00-workflow.md#w5).

**Аналитика на боевой базе.** Тяжёлый запрос вытесняет данные из буферного пула и удерживает старые версии строк, деградируя пользовательские операции. → Разделение контуров ([T-045](topics/03-storage-and-data.md#oltp-olap)).

**Деньги в числе с плавающей точкой.** Ошибки округления накапливаются и обнаруживаются сверкой через месяцы. → Целое в минимальных единицах или десятичный тип ([T-034](topics/03-storage-and-data.md#data-types)).

**Будущее событие сохранено в UTC.** Изменение правил часового пояса сдвигает встречу. → Локальное время плюс идентификатор зоны.

**Отключённые ограничения БД «ради производительности».** Внешние ключи и уникальные индексы — самый дешёвый эшелон целостности; без них расхождения появляются тихо. → Оставить ограничения, оптимизировать иначе ([T-046](topics/03-storage-and-data.md#data-integrity)).

**Миграция одним изменением.** Во время выката работают обе версии кода; удаление или переименование колонки ломает старую. → expand → backfill → переключение → contract ([T-047](topics/03-storage-and-data.md#migrations)).

**Забытый шаг contract.** Двойная запись и старая колонка остаются навсегда, система живёт в переходном состоянии. → Планировать удаление сразу, с датой.

<a id="cache"></a>

## Кэш

**Кэш поверх неоптимального запроса.** Проблема скрыта до первого массового промаха, после которого БД получает стократную нагрузку. → Сначала оптимизировать запрос ([T-132](topics/11-performance-and-cost.md#api-performance)).

**Обновление кэша после записи.** Два процесса записывают в кэш в порядке, обратном порядку записи в БД. → Удаление ключа, а лучше версионирование ключа ([T-052](topics/04-caching.md#cache-invalidation)).

**Одинаковый TTL у всех ключей.** Ключи, созданные одновременно, истекают одновременно — БД получает залп. → Случайный разброс ±10–20 %.

**Отсутствие защиты от лавины на популярном ключе.** Тысяча параллельных запросов идёт в БД за одним значением. → Блокировка на пересчёт, объединение запросов, вероятностное раннее обновление ([T-053](topics/04-caching.md#cache-pathologies)).

**Нет кэширования отсутствия.** Запросы за несуществующими данными каждый раз доходят до БД — простой способ её перегрузить. → Кэшировать сам факт отсутствия с коротким TTL.

**Инвалидация из кода приложения вне транзакции.** Транзакция откатилась, а в кэше уже новое значение — данные, которых нет в БД. → Инвалидация по журналу изменений БД.

<a id="async"></a>

## Асинхронность

**Двойная запись: в БД и в брокер.** Публикация упала после коммита — событие потеряно навсегда; откатилась транзакция после публикации — подписчики узнали о том, чего не было. → Transactional outbox или CDC ([T-061](topics/05-async-and-messaging.md#outbox)).

**Событие в повелительном наклонении.** `ОтправитьУведомление` вместо `ЗаказОплачен` возвращает связность: издатель снова знает, кто и что должен сделать. → Событие — факт в прошедшем времени ([T-055](topics/05-async-and-messaging.md#interaction-models)).

**Потребитель без идемпотентности.** Доставка at-least-once — норма, значит дубликаты гарантированы. → Отметка об обработке в одной транзакции с эффектом ([T-060](topics/05-async-and-messaging.md#delivery-guarantees)).

**Бесконечный повтор сбойного сообщения.** «Ядовитое» сообщение в упорядоченном логе останавливает партицию навсегда. → Классификация ошибок, ограниченное число попыток, DLQ ([T-062](topics/05-async-and-messaging.md#consumer-retries)).

**DLQ без мониторинга.** Очередь молча накапливает потерянные бизнес-операции — самый распространённый способ «потерять» платежи. → Алерт на любое ненулевое значение для критичных потоков.

**Неограниченная очередь в памяти.** Разница между темпом производителя и потребителя копится до исчерпания памяти. → Ограниченные буферы и backpressure ([T-063](topics/05-async-and-messaging.md#backpressure)).

**Обещание exactly-once.** Свойство приписывается брокеру, хотя относится ко всей цепочке. → At-least-once плюс дедупликация.

<a id="distributed"></a>

## Распределённость

**Распределённая транзакция там, где нужна одна.** Сущности, всегда меняющиеся вместе, разнесены по сервисам — признак неверной границы. → Пересмотреть границы, а не строить сагу ([T-078](topics/07-architecture-styles.md#boundaries)).

**Сага без учёта отсутствия изоляции.** Промежуточные состояния видны другим, и на них принимаются решения. → Явные статусы и семантические блокировки ([T-073](topics/06-distributed-systems.md#distributed-transactions)).

**Компенсация, которая не может упасть.** Компенсирующее действие считается всегда успешным, хотя это обычный сетевой вызов. → Идемпотентная повторяемая компенсация.

**Блокировка на TTL без ограждающего маркера.** Держатель «проснулся» после паузы и продолжает работу, считая себя владельцем. → Fencing token, отвергающий устаревшие операции ([T-072](topics/06-distributed-systems.md#distributed-locks)).

**Разрешение конфликтов по метке времени.** Часы узлов расходятся; «последняя» запись определяется неверно, данные теряются молча. → Логические версии, разрешение в приложении или CRDT ([T-075](topics/06-distributed-systems.md#conflicts)).

**Случайный UUID как первичный ключ большой таблицы.** Вставки идут в случайные места индекса, страницы фрагментируются, запись деградирует. → Время-упорядоченные идентификаторы ([T-074](topics/06-distributed-systems.md#unique-ids)).

**Корректность, опирающаяся только на детектор отказов.** Ложное объявление лидера мёртвым даёт двух лидеров. → Кворум и ограждающий маркер как страховка ([T-071](topics/06-distributed-systems.md#failure-detection)).

<a id="reliability"></a>

## Надёжность

**Сетевой вызов без таймаута.** Один зависший вызов занимает поток до бесконечности; сотня таких исчерпывает пул, и отказ зависимости становится отказом сервиса. → Таймаут на каждом вызове, из бюджета задержки ([T-090](topics/08-reliability.md#timeouts-retries)).

**Повторы без джиттера и без бюджета.** Клиенты синхронизируются и добивают восстанавливающуюся систему. → Экспонента с полным джиттером плюс ограничение доли повторов.

**Повторы на каждом уровне.** Три уровня по три попытки дают 27 запросов вместо одного. → Повторяет один слой.

**Health check, зависящий от общей БД.** При кратковременном сбое БД **все** экземпляры объявляют себя нездоровыми, и система падает полностью вместо частичной деградации. → Liveness проверяет только процесс ([T-094](topics/08-reliability.md#health-checks)).

**Отсутствие приоритетов при сбросе нагрузки.** Отказ бьёт случайно и с равной вероятностью попадает по оформлению заказа и по рекомендациям. → Классы приоритета ([T-092](topics/08-reliability.md#load-shedding)).

**Резервный регион, на который никогда не переключались.** Конфигурация разъехалась, квоты не выданы, образы устарели — узнаётся в момент аварии. → Регулярные учения ([T-099](topics/08-reliability.md#chaos)).

**Бэкап без проверки восстановлением.** Файлы есть, восстановиться нельзя — обнаруживается в худший момент. → Автоматический прогон восстановления ([T-098](topics/08-reliability.md#backup-dr)).

**Механики устойчивости без наблюдаемости.** Circuit breaker, деградация и ретраи есть, но не видно, срабатывают ли они. → Состояние каждого механизма как метрика.

<a id="security"></a>

## Безопасность

**Проверка прав только по факту аутентификации.** Токен валиден — доступ дан; смена идентификатора в адресе открывает чужие данные. Самая частая уязвимость. → Авторизация на уровне объекта в слое доступа к данным ([T-103](topics/09-security.md#authorization)).

**Фильтрация вместо разделения данных и кода.** Чёрные списки и экранирование «опасных» символов обходятся; защита строится не там. → Параметризованные запросы, контекстное экранирование при выводе, белые списки адресов ([T-106](topics/09-security.md#attacks)).

**Доверие к полю алгоритма в токене.** Проверяющая сторона берёт алгоритм из самого токена. → Ожидаемый алгоритм задаётся конфигурацией ([T-101](topics/09-security.md#jwt)).

**Долгоживущий токен без возможности отзыва.** Утечка действует до истечения срока, а он год. → Короткий токен доступа плюс отзываемый токен обновления.

**Секреты в репозитории или в переменных образа.** Секрет, попавший в историю системы контроля версий, считается скомпрометированным. → Хранилище секретов и ротация ([T-107](topics/09-security.md#encryption)).

**Персональные данные в логах и трассировках.** Утечка через систему, которую не считают хранилищем. → Явные правила того, что не логируется ([T-111](topics/09-security.md#audit)).

**Плавающие версии зависимостей.** В прод попадает то, чего никто не проверял; компрометация пакета доходит автоматически. → Файл блокировки, проверка уязвимостей, внутреннее зеркало ([T-109](topics/09-security.md#supply-chain)).

**CORS как защита сервера.** Разрешения ослабляются в расчёте на то, что браузер что-то охраняет; `curl` про CORS не знает. → Авторизация на сервере независимо от CORS ([T-019](topics/01-network-and-api.md#cors)).

<a id="ops"></a>

## Эксплуатация

**Алерт на каждую аномалию.** Дежурного будят из-за всплеска, прошедшего самого; через месяц уведомления не читают, и настоящая авария теряется. → Алерты по симптомам и по расходу бюджета ошибок ([T-121](topics/10-delivery-and-ops.md#alerting)).

**Метка с идентификатором пользователя в метрике.** Кардинальность умножается на миллионы, система мониторинга падает. → Метки с ограниченным набором значений; детали в логи и трассировку ([T-119](topics/10-delivery-and-ops.md#observability-cost)).

**Логи без идентификатора запроса.** Распределённый запрос не собирается в единую картину. → Сквозной контекст во всех трёх сигналах ([T-118](topics/10-delivery-and-ops.md#observability)).

**Нестабильные тесты.** После нескольких ложных падений красную сборку перезапускают не глядя — конвейер перестаёт что-либо гарантировать. → Чинить или удалять ([T-123](topics/10-delivery-and-ops.md#testing)).

**Ручные правки поверх кода инфраструктуры.** Следующее применение внезапно откатывает чужие изменения. → Только через код, регулярная проверка расхождения ([T-117](topics/10-delivery-and-ops.md#config)).

**Пересборка артефакта для прода.** Тестировали не то, что выкатили. → Одна сборка на все окружения, различия только в конфигурации.

**Задача по расписанию без контроля запуска.** Пропущенный запуск не вызывает ошибок и потому невидим. → Сторожевой мониторинг по факту завершения ([T-084](topics/07-architecture-styles.md#background-jobs)).

**Kubernetes ради Kubernetes.** Три сервиса и редкие выкатки не окупают сложности кластера. → Соразмерять инструмент задаче ([T-116](topics/10-delivery-and-ops.md#kubernetes)).

<a id="perf"></a>

## Производительность и стоимость

**Оптимизация без измерения.** Недели уходят на участок, дающий два процента. → Профилирование до оптимизации ([T-136](topics/11-performance-and-cost.md#profiling)).

**Среднее время ответа как показатель.** Среднее 80 мс совместимо с тем, что каждый двадцатый запрос идёт две секунды. → Перцентили по сценариям ([T-129](topics/11-performance-and-cost.md#percentiles)).

**Усреднение перцентилей между узлами.** Среднее из p99 десяти серверов не является p99 системы — цифра на дашборде не значит ничего. → Агрегировать гистограммы.

**N+1 запросов.** Сто запросов вместо одного; на тестовых данных незаметно. → Счётчик запросов на сценарий как метрика ([T-133](topics/11-performance-and-cost.md#pooling)).

**Огромный пул соединений.** Лишние соединения не ускоряют базу, а создают конкуренцию и ухудшают время ответа для всех. → Размер подбирается измерением, обычно десятки.

**Планирование ёмкости под 100 % загрузки.** Задержка растёт нелинейно и деградация наступает задолго до исчерпания ресурсов. → Целевая загрузка 60–70 % ([T-134](topics/11-performance-and-cost.md#queueing)).

**Нагрузочный тест с падающим темпом.** Генератор ждёт ответа и сам снижает нагрузку — измеренная задержка занижена именно тогда, когда система работает хуже всего. → Постоянный темп независимо от ответов ([T-135](topics/11-performance-and-cost.md#load-testing)).

**Автомасштабирование без верхнего предела.** Всплеск трафика или цикл повторов превращается в счёт на порядок больше ([T-122](topics/10-delivery-and-ops.md#capacity)).

**Стоимость считается только по инфраструктуре.** Наблюдаемость, исходящий трафик и труд на эксплуатацию часто больше счёта за серверы. → Полная стоимость владения и unit-экономика ([T-138](topics/11-performance-and-cost.md#cost)).
