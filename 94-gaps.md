# Пробелы плейлиста и что добавлено

Плейлист ByteByteGo хорошо объясняет **механики отдельных компонентов** (что такое Kafka, как работает CDN, чем JWT отличается от сессии) и почти не касается **процесса проектирования** и **корректности под нагрузкой** (согласованность, распределённые транзакции, устойчивость к отказам, эксплуатация).

Ниже — что добавляется сверх плейлиста. Каждый пункт помечен: `нет` — темы в плейлисте нет вообще; `частично` — задета вскользь в видео другого топика.

---

## B00 · Процесс проектирования

| Тема | Статус | Зачем нужна |
|---|---|---|
| Сбор требований: FR / NFR, ограничения, допущения | нет | Без этого дизайн не проверяем: непонятно, что считать успехом |
| SLI / SLO / error budget | нет | Численная цель, из которой выводятся резервирование, ретраи и стоимость |
| Оценки на салфетке: RPS, объём, трафик, бюджет задержки | частично (#3 — только числа задержек) | Определяет, нужен ли вообще шардинг/кэш, или хватит одной БД |
| ADR (запись архитектурных решений) | нет | Фиксирует «почему», а не только «как»; иначе решение переигрывают через полгода |
| Чек-лист design review | частично (#98 — ошибки на интервью) | Повторяемая процедура проверки чужого и своего дизайна |

Источники: Google SRE Book (гл. «Service Level Objectives»), Michael Nygard «Documenting Architecture Decisions», arc42 / C4 model.

## B01 · Сеть, протоколы, API

| Тема | Статус | Зачем нужна |
|---|---|---|
| WebSocket / SSE / long polling — выбор транспорта для push | нет | Любая realtime-фича (чат, лента, уведомления) начинается с этого выбора |
| Идемпотентность запросов, idempotency key | нет | Без неё повтор при таймауте = двойной платёж |
| Версионирование API и обратная совместимость | нет | Определяет, можно ли выкатывать клиент и сервер независимо |
| Contract-first: OpenAPI, protobuf, schema registry | частично (#16 gRPC) | Контракт как артефакт, а не как документация постфактум |
| Эволюция схемы в gRPC/Kafka (совместимость вперёд/назад) | нет | Ломающее изменение схемы кладёт консьюмеров тише и позже, чем хотелось бы |

Источники: RFC 6455 (WebSocket), WHATWG HTML — Server-Sent Events, Stripe API docs (idempotency), Confluent Schema Registry docs.

## B02 · Приём трафика

| Тема | Статус | Зачем нужна |
|---|---|---|
| Rate limiting: token bucket, leaky bucket, sliding window | нет | Базовая защита от перегрузки и злоупотреблений; классическая задача дизайна |
| Service discovery и регистрация сервисов | нет | Без неё адреса зашиты в конфиг и деплой становится ручным |
| L4 vs L7 балансировка, health checks, sticky sessions | частично (#40, #87) | Влияет на то, переживёт ли система выкатку и падение узла |
| Anycast, GSLB, multi-region маршрутизация | нет | Точка входа для географически распределённой системы |

Источники: Cloudflare Learning Center (rate limiting, anycast), Envoy Proxy docs, Consul / etcd docs.

## B03 · Хранилища и данные

| Тема | Статус | Зачем нужна |
|---|---|---|
| Моделирование данных от паттернов доступа | нет | Выбор БД без access patterns — гадание |
| Индексы: B-tree vs LSM, покрывающие, составные | частично (#5) | Объясняет, почему запись быстрая, а чтение — нет (и наоборот) |
| Уровни изоляции и аномалии, MVCC, блокировки | нет (есть только ACID #60) | «Транзакция есть» ≠ «гонок нет»: read committed пропускает write skew |
| Репликация: sync/async, лаг, read-your-writes | частично (#68) | Определяет, увидит ли пользователь свою же запись |
| Шардинг: выбор ключа, ребалансировка, hot partition | частично (#68) | Неверный ключ шардирования — самая дорогая ошибка в дизайне данных |
| Consistent hashing | нет | Механика, без которой не объяснить ни шардинг, ни распределённый кэш |
| Object / blob storage, presigned URL | нет | Файлы и медиа не хранят в БД, но в дизайне про это забывают |
| OLTP vs OLAP, разделение контуров | частично (#101 lakehouse) | Аналитика на боевой БД — типовая причина деградации |
| Zero-downtime миграции, expand/contract, бэкфиллы | нет | Схема меняется чаще, чем архитектура; это отдельный навык |
| Мультитенантность: изоляция данных | нет | Определяет модель БД для любого B2B-продукта |
| Retention, удаление, GDPR/152-ФЗ | нет | Требование, влияющее на схему и на бэкапы |

Источники: Kleppmann «Designing Data-Intensive Applications» (гл. 3, 5, 6, 7), PostgreSQL docs (Transaction Isolation), Jepsen (consistency models), Amazon Dynamo paper (consistent hashing).

## B04 · Кэширование

| Тема | Статус | Зачем нужна |
|---|---|---|
| Стратегии: cache-aside / write-through / write-behind / read-through | частично (#6) | Определяет, где живёт истина и что теряется при падении |
| Согласованность кэша и БД, инвалидация, TTL vs событие | частично (#57) | Главный источник «данные из прошлого» в проде |
| Cache stampede, hot key, negative caching | частично (#57) | Отказ кэша обычно роняет БД, а не деградирует плавно |
| Локальный кэш vs распределённый, near-cache | нет | Компромисс между задержкой и согласованностью |

Источники: AWS Caching Best Practices, Redis docs (client-side caching), Facebook «Scaling Memcache at Facebook» (NSDI 2013).

## B05 · Асинхронность и обмен сообщениями

| Тема | Статус | Зачем нужна |
|---|---|---|
| Гарантии доставки: at-most / at-least / exactly-once, дедупликация | нет | «Exactly-once» продают как галочку, а это свойство всей цепочки |
| Transactional outbox, CDC | нет | Единственный честный способ атомарно записать в БД и в очередь |
| DLQ, ретраи консьюмера, poison message | нет | Без этого один битый месседж останавливает партицию |
| Backpressure и flow control | нет | Определяет, деградирует система или падает |
| Очередь vs лог: семантика и последствия | частично (#67) | Выбор между RabbitMQ и Kafka — это не про производительность |
| Батч vs стрим, оконные агрегации | частично (#66) | Разные требования к задержке и к пересчёту |

Источники: Kleppmann DDIA (гл. 11), Confluent docs (exactly-once semantics), microservices.io (Transactional Outbox), Debezium docs.

## B06 · Распределённые системы

| Тема | Статус | Зачем нужна |
|---|---|---|
| Модели согласованности: linearizability, causal, eventual; PACELC | частично (#13 CAP, #65 BASE) | CAP без моделей согласованности не даёт принять ни одного решения |
| Консенсус: Raft / Paxos, кворумы, leader election | нет | Лежит под каждым «надёжным» хранилищем и координатором |
| Кворумы чтения/записи (R + W > N) | нет | Настройка, которой регулируют компромисс задержка/свежесть |
| Распределённые блокировки и аренда (lease) | нет | Классический источник тихих багов (см. критику Redlock) |
| Распределённые транзакции: 2PC, saga, TCC | нет | Как только процессов больше одного — это главный вопрос корректности |
| Генерация уникальных ID: Snowflake, UUIDv7, ULID | нет | Влияет на сортировку, на индексы и на шардинг |
| Логические часы, версии, разрешение конфликтов, CRDT | нет | Нужны везде, где возможна параллельная запись |

Источники: Raft paper (Ongaro, Ousterhout), Google Spanner paper, Martin Kleppmann «How to do distributed locking», microservices.io (Saga), Jepsen consistency map.

## B07 · Архитектурные стили

| Тема | Статус | Зачем нужна |
|---|---|---|
| Модульный монолит и границы контекстов (DDD) | нет | Микросервисы без границ = распределённый монолит |
| Event-driven архитектура, хореография vs оркестрация | нет | Определяет связность и наблюдаемость процесса |
| CQRS и event sourcing | нет | Разделение путей чтения и записи; аудит как побочный эффект |
| Strangler fig — миграция монолита | нет | Дизайн «с нуля» встречается реже, чем миграция |
| Service mesh / sidecar, BFF | нет | Куда уезжают ретраи, mTLS и трассировка из кода сервисов |

Источники: Eric Evans «Domain-Driven Design», Martin Fowler (CQRS, StranglerFigApplication, MonolithFirst), Sam Newman «Building Microservices».

## B08 · Надёжность и отказоустойчивость

Самый большой пробел: **одно видео (#90) на весь блок.**

| Тема | Статус | Зачем нужна |
|---|---|---|
| Таймауты, ретраи, exponential backoff + jitter | нет | Ретраи без jitter превращают сбой в лавину |
| Circuit breaker, bulkhead, fail fast | нет | Локализация отказа вместо каскада |
| Graceful degradation, feature flag / kill switch | нет | Частичная работа лучше полной недоступности |
| Health checks: liveness vs readiness | нет | Неверная проверка удаляет живые узлы под нагрузкой |
| Multi-region: active-active / active-passive, failover | нет | Требование доступности выше 99.9% решается только так |
| DR: RPO / RTO, бэкапы и проверка восстановления | нет | Непроверенный бэкап — это не бэкап |
| Chaos engineering, game days | нет | Проверка гипотез об отказах до того, как их проверит прод |
| Идемпотентные ретраи и дедупликация на стороне сервера | нет | Обратная сторона ретраев |

Источники: Michael Nygard «Release It!», AWS Well-Architected — Reliability Pillar, AWS Builders' Library (timeouts, retries, backoff, jitter), Google SRE Book.

## B09 · Безопасность

| Тема | Статус | Зачем нужна |
|---|---|---|
| Модели авторизации: RBAC / ABAC / ReBAC | нет | Аутентификация есть в плейлисте, авторизации нет вовсе |
| Threat modeling (STRIDE), поверхность атаки | нет | Систематический способ не забыть про угрозу |
| Шифрование at rest / in transit, KMS, ротация ключей | нет | Требование почти любого регламента |
| Управление секретами | нет | Секрет в переменной окружения — типовая утечка |
| mTLS, zero trust между сервисами | нет | Внутренняя сеть перестала считаться доверенной |
| Аудит действий и трассируемость | нет | Требование для финансов, медицины, госсектора |

Источники: OWASP Top 10 и OWASP API Security Top 10, NIST SP 800-207 (Zero Trust), Google BeyondCorp, RFC 6749 / RFC 9700 (OAuth 2 Security BCP).

| Тема | Статус | Зачем нужна |
|---|---|---|

| IaC, конфигурация как код | нет | Воспроизводимость окружений |

Источники: Google SRE Book и SRE Workbook, OpenTelemetry docs, Brendan Gregg «Systems Performance».

## B11 · Производительность и стоимость

| Тема | Статус | Зачем нужна |
|---|---|---|
| Перцентили p50/p95/p99, tail latency, coordinated omission | частично (#3) | Среднее время ответа не описывает пользовательский опыт |
| Connection pooling, N+1, batching | нет | Самые частые причины «непонятной» деградации |
| Закон Литтла и очереди, насыщение | нет | Объясняет, почему при 80% загрузки задержка растёт нелинейно |
| FinOps: TCO, unit-экономика запроса | частично (#28) | Стоимость — такое же нефункциональное требование, как задержка |

Источники: Gil Tene «How NOT to Measure Latency», Brendan Gregg (USE method), AWS Well-Architected — Cost Optimization Pillar.

## B12 · Кейсы

В плейлисте есть **разборы чужих архитектур** (Discord, Netflix, Stack Overflow, Hotstar, Google, Prime Video), но нет ни одного **пошагового проектирования с нуля** — а именно этот навык документ должен тренировать.

Добавляются сквозные разборы по `00-workflow.md`:

- подробно: **сокращатель ссылок**, **лента новостей**, **чат/мессенджер**;
- кратко: rate limiter, сервис уведомлений, автодополнение поиска, загрузка и раздача видео, бронирование билетов (борьба за дефицитный ресурс), платёжный поток (идемпотентность + saga), геопоиск ближайших объектов, дедупликация и top-K.

Источники: Alex Xu «System Design Interview» vol. 1–2 (задачи), инженерные блоги Discord / Netflix / Uber / Cloudflare (для проверки решений о реальные системы).
