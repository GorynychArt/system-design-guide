# B03 · Хранилища и данные

Слой, где решения дороже всего откатывать. Схема, ключ шардирования и выбор хранилища переживают несколько поколений кода: сервис можно переписать за квартал, а форму хранения десяти терабайт — нет.

Плейлист покрывает блок обзорно (6 видео) и целиком в реляционной логике, поэтому тринадцать из девятнадцати карточек добавлены: изоляция транзакций, шардирование, эволюция схемы, специализированные хранилища, геоданные, типы данных и сверка.

## DATA-01 · Выбор хранилища

🎬 [#1](https://www.youtube.com/watch?v=lX4CrbXMsNQ), [#68](https://www.youtube.com/watch?v=_1IKwnbscQU) · шаг [W3](../00-workflow.md#w3)

**TL;DR.** Реляционная БД — разумное умолчание. Отклонение от умолчания требует довода в виде числа или формы данных, а не моды.

**Проблема.** Выбор хранилища обычно делают до формулировки паттернов доступа — по привычке, по резюме или по статье о том, как некая компания с миллиардом пользователей ушла от PostgreSQL. Ошибка обнаруживается через год, когда переписывать поздно: неверный класс хранилища либо не даёт нужный запрос, либо не держит нужную нагрузку, либо требует эксплуатации, на которую нет людей.

**Как работает — критерии выбора.**
- **Форма данных.** Связи и агрегаты, требующие соединений, → реляционная. Документы, читаемые целиком, → документная. Граф связей с обходом в глубину → графовая. Метрики по времени → time-series. Ключ-значение с высокой частотой → KV-хранилище.
- **Профиль нагрузки.** Записей больше, чем чтений, и они append-only → LSM-хранилища ([DATA-05](#indexes)). Чтения преобладают → реляционная с репликами и кэшем.
- **Объём и рост.** До единиц терабайт и десятков тысяч операций в секунду одна реляционная БД справляется — этого достаточно подавляющему большинству систем.
- **Требования к согласованности.** Нужны транзакции над несколькими сущностями → реляционная. Достаточно атомарности одного документа → документная.
- **Операционная стоимость.** Каждое новое хранилище — это бэкапы, мониторинг, обновления, экспертиза и дежурство. Второе хранилище стоит дороже, чем кажется на этапе выбора.

**Когда применять что**

| Класс | Сильная сторона | Плата |
|---|---|---|
| Реляционная (PostgreSQL, MySQL) | Транзакции, соединения, зрелость, гибкость запросов | Масштабирование записи требует шардирования |
| Документная (MongoDB, DocumentDB) | Гибкая схема, агрегат целиком | Слабые межколлекционные операции |
| Wide-column (Cassandra, ScyllaDB) | Огромная нагрузка на запись, линейный рост | Запросы только по заранее выбранному ключу |
| KV (Redis, DynamoDB) | Минимальная задержка, простота | Нет сложных запросов |
| Поисковая (Elasticsearch) | Полнотекстовый и фасетный поиск | Не источник истины ([DATA-13](#search)) |
| Колоночная (ClickHouse, BigQuery) | Аналитика по миллиардам строк | Плохо для точечных обновлений |
| Object storage (S3) | Дёшево, безгранично для файлов | Нет запросов по содержимому |

**Trade-offs и режимы отказа.** Polyglot persistence умножает не только возможности, но и число мест, где данные расходятся: любые две копии требуют механизма синхронизации ([MSG-07](05-async-and-messaging.md#outbox)). Специализированное хранилище решает одну задачу отлично и мстит за все остальные запросы. Выбор «как в Netflix» переносит решение, принятое под чужие числа.

**Что мерить.** Задержка и пропускная способность по каждому паттерну доступа, объём и его рост, доля запросов, не покрытых индексом, стоимость хранения и операций.

## DATA-02 · Специализированные хранилища: time-series, графовые, векторные

➕ добавлено · шаг [W3](../00-workflow.md#w3)

**TL;DR.** Реляционная БД тянет почти всё, но на трёх профилях нагрузки проигрывает на порядки: поток метрик, обход графа связей и поиск по близости в векторном пространстве.

**Проблема.** Каждый из этих профилей ломает предположения, на которых построена реляционная модель. Метрики — это миллионы записей в секунду, которые почти никогда не читают поштучно, зато агрегируют по временным окнам. Обход графа «друзья друзей друзей» превращается в соединение таблицы с собой на каждом уровне, и стоимость растёт экспоненциально. Поиск похожего по эмбеддингу вообще не выражается через сравнение значений: нужен поиск ближайших точек в пространстве сотен измерений.

**Три класса.**

**Time-series** (Prometheus, VictoriaMetrics, TimescaleDB, ClickHouse). Данные — точки «метрика + набор меток + время + значение». Специализация даёт три вещи: сжатие, использующее монотонность времени и близость соседних значений (дельта-кодирование и XOR — приём из Gorilla, дающий кратное сокращение против общего сжатия); автоматическое прореживание старых данных и удаление по возрасту; запросы, выражающие окна и агрегаты как примитивы. Главный ограничитель — **кардинальность**: каждая уникальная комбинация меток создаёт отдельный ряд, и метка с идентификатором пользователя убивает систему мониторинга быстрее любой нагрузки ([OPS-08](10-delivery-and-ops.md#observability-cost)).

**Графовые** (Neo4j, JanusGraph). Связь хранится как ссылка, а не как строка в таблице соединений, поэтому переход к соседям стоит примерно константу независимо от размера графа. Оправданы там, где обход глубже трёх уровней и глубина заранее неизвестна: рекомендации по социальному графу, права доступа вида ReBAC ([SEC-04](09-security.md#authorization)), цепочки в антифроде. До двух-трёх уровней рекурсивный запрос в PostgreSQL справляется — и это правильный первый шаг.

**Векторные** (pgvector, Qdrant, Milvus, поиск по векторам в Elasticsearch). Хранят эмбеддинги и ищут ближайшие приближённо: точный поиск в многомерном пространстве стоит полного перебора, поэтому используются индексы вроде HNSW — графа связей между точками, по которому спуск ведёт к близким соседям. Ключевой параметр — **компромисс между полнотой и скоростью**: индекс настраивается так, что часть по-настоящему ближайших соседей теряется, и это осознанный размен. Применение: семантический поиск, поиск дубликатов, рекомендации, извлечение контекста для языковых моделей. На практике почти всегда работает гибрид с обычным полнотекстовым поиском ([DATA-13](#search)).

**Правило подхода.** Сначала расширить основную БД — расширением для векторов, рекурсивным запросом для графа, колоночной таблицей для метрик; и только когда упирается, вводить отдельную систему. Каждое новое хранилище стоит эксплуатации, синхронизации и сверки ([DATA-16](#data-integrity)).

**Альтернативы**

| Задача | Лёгкий путь | Тяжёлый путь |
|---|---|---|
| Метрики | Колоночная таблица, ClickHouse рядом | Специализированная TSDB с прореживанием |
| Граф | Рекурсивный запрос в SQL | Графовая БД с языком обхода |
| Векторы | Расширение к PostgreSQL | Отдельный векторный движок с шардированием |

**Trade-offs и режимы отказа.** Все три класса дают производную копию данных, которая расходится с источником — нужен конвейер ([MSG-07](05-async-and-messaging.md#outbox)) и сверка. Смена модели эмбеддингов означает полную переиндексацию всего корпуса: это плановая работа на часы, её закладывают заранее. Графовые БД плохо шардируются — связный граф трудно разрезать. Прореживание метрик необратимо: детализация за прошлый год не восстановится.

**Что мерить.** Для метрик — число рядов и рост кардинальности; для графа — глубина и время обхода; для векторов — полнота выдачи на контрольном наборе и задержка поиска, а также доля запросов, где гибридная выдача лучше чистой векторной.

**Связано:** [DATA-01 выбор хранилища](#storage-choice) · [DATA-13 полнотекстовый поиск](#search) · [DATA-15 OLTP/OLAP](#oltp-olap) · [DATA-16 целостность](#data-integrity)

**Источники:** [Gorilla: A Fast, Scalable, In-Memory Time Series Database (VLDB 2015)](https://www.vldb.org/pvldb/vol8/p1816-teller.pdf) · [Prometheus — Storage](https://prometheus.io/docs/prometheus/latest/storage/) · [Malkov & Yashunin — Efficient and robust ANN search using HNSW](https://arxiv.org/abs/1603.09320) · [pgvector](https://github.com/pgvector/pgvector) · [Neo4j — Graph database concepts](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/)

## DATA-03 · Моделирование от паттернов доступа

➕ добавлено · шаг [W3](../00-workflow.md#w3)

**TL;DR.** Сначала список запросов с их частотой и требованиями к задержке, потом схема. Не наоборот.

**Проблема.** Схема, спроектированная «правильно» с точки зрения нормализации, может не обслуживать главный запрос системы: он требует шести соединений и сортировки миллиона строк. Обратная крайность — денормализация везде — превращает каждое изменение в каскад обновлений. Без явного списка паттернов доступа выбор между ними делается наугад.

**Как работает.**
1. **Выписать запросы**: что читаем, по какому ключу, сколько строк, с какой частотой, с каким требованием к задержке и свежести. Формулировка вида «лента пользователя, последние 20 записей, 5 000 RPS, p99 200 мс, допустимо отставание 10 с».
2. **Ранжировать**: 2–3 запроса обычно дают 90 % нагрузки. Схема оптимизируется под них, остальные обслуживаются как получится.
3. **Спроектировать ключи и индексы** под запросы из шага 1 ([DATA-05](#indexes)).
4. **Решить про денормализацию точечно**: дублируем поле, если оно читается на порядок чаще, чем меняется, и рассогласование заметно не сразу.
5. **Развести истину и проекции.** Источник истины нормализован; быстрые чтения обслуживают производные структуры — материализованные представления, поисковый индекс, кэш, отдельная модель чтения ([ARCH-06](07-architecture-styles.md#cqrs)).

**Когда применять.** Всегда — но глубина проработки пропорциональна цене ошибки: для wide-column и документных хранилищ схема **полностью** определяется запросами, для реляционных остаётся пространство для манёвра.

**Альтернативы**

| Подход | Когда лучше | Цена |
|---|---|---|
| Нормализованная схема | Запросы разнообразны и заранее неизвестны | Соединения на горячем пути |
| Денормализация | Известен доминирующий запрос | Каскадные обновления, риск рассогласования |
| Материализованные представления | Тяжёлая агрегация читается часто | Задержка обновления, стоимость пересчёта |
| Отдельная модель чтения (CQRS) | Профили чтения и записи расходятся радикально | Второй контур данных и его согласование |

**Trade-offs и режимы отказа.** Денормализация без владельца поля приводит к тому, что копии расходятся и никто не знает, какая верна. Оптимизация под сегодняшний главный запрос усложняет появление завтрашнего. Схема, выведенная из UI-экранов, ломается при первом редизайне — выводить нужно из сущностей и операций домена, а из экранов брать только частоты.

**Что мерить.** Доля запросов, обслуженных индексом; число строк, прочитанных на один возвращённый; частота изменения денормализованных полей; отставание проекций.

## DATA-04 · Типы данных: деньги, время, идентификаторы

➕ добавлено · шаг [W3](../00-workflow.md#w3)

**TL;DR.** Ошибки в этом слое не видны на тестах, накапливаются молча и обнаруживаются сверкой через месяцы. Правила простые, но их надо принять один раз и на всю схему.

**Проблема.** `0.1 + 0.2` в двоичной плавающей точке не равно `0.3`. Встреча, назначенная на 9:00 по местному времени, «переезжает» после смены правил перехода на летнее время. Сумма, посчитанная в трёх местах с разным округлением, расходится на копейки, и расхождение растёт с оборотом. Каждая из этих ошибок дешева в момент проектирования схемы и очень дорога потом.

**Деньги.**
- **Никогда не хранить в числе с плавающей точкой.** Только целое в минимальных единицах (копейки, центы) либо десятичный тип фиксированной точности.
- **Валюта хранится рядом с суммой** и является частью значения: сумма без валюты — не сумма. Код валюты по ISO 4217.
- **Округление — это правило и место.** Правило (половина вверх, банковское) фиксируется явно; место — одно: округлять на каждом промежуточном шаге значит накапливать погрешность. Распределение суммы по позициям (скидка на корзину, налог) требует алгоритма, который гарантирует, что части складываются в целое.
- **Курс конвертации фиксируется на момент операции** и хранится вместе с ней, иначе исторические суммы «плывут» при пересчёте.

**Время.**
- **Момент события — в UTC.** Метки создания, изменения, логи — только так.
- **Будущее событие в календаре — исключение.** «Совещание 12 марта в 9:00 по Москве» нужно хранить как локальное время плюс идентификатор зоны IANA: если правила зоны изменятся, момент в UTC обязан пересчитаться. Хранение такого события сразу в UTC — тихая ошибка, которая проявится через год.
- **Переходы на летнее время** дают несуществующие и удвоенные моменты: 02:30 в день перехода может не существовать либо существовать дважды. Любая арифметика над локальным временем обязана это учитывать.
- **База часовых поясов обновляется** несколько раз в год — её версия является зависимостью системы, а не деталью операционной системы.
- **Сутки не равны 24 часам**, месяц — переменной длины: «плюс один день» и «плюс 24 часа» — разные операции.
- **Длительность измеряется монотонными часами**, а не настенными: коррекция времени может пойти назад и дать отрицательную длительность ([DIST-10](06-distributed-systems.md#conflicts)).

**Идентификаторы и строки.**
- Тип идентификатора в схеме выбирается один раз и переживает всё остальное ([DIST-09](06-distributed-systems.md#unique-ids)).
- Порядковый публичный идентификатор раскрывает объёмы бизнеса — наружу отдают непрозрачный.
- Электронная почта — плохой первичный ключ: она меняется, регистр части адреса формально значим, а варианты с плюсом дают несколько написаний одного ящика.
- Текст нормализуется по Unicode перед сравнением и хранением; ограничения длины считаются в символах, а не в байтах, иначе имя с эмодзи неожиданно не помещается.
- Значения перечислений не переиспользуются: удалённый статус остаётся в истории, и его код не должен означать что-то другое.

**Trade-offs и режимы отказа.** Целое в копейках упирается в разрядность при очень больших суммах и требует внимания к валютам без дробной части. Хранение локального времени с зоной усложняет запросы по диапазону — на практике держат оба представления, помечая, какое из них источник истины. Строгая нормализация строк ломает поиск по «как ввёл пользователь», поэтому хранят и исходное написание, и нормализованную форму для сравнения.

**Что мерить.** Расхождения при сверке сумм ([DATA-16](#data-integrity)), число операций с округлением в отчётный период, ошибки разбора дат по источникам, доля записей с неизвестной или пустой зоной времени.

## DATA-05 · Индексы: B-tree, LSM, составные и покрывающие

🎬 [#5](https://www.youtube.com/watch?v=ouipSd_5ivQ) · шаг [W3](../00-workflow.md#w3)

**TL;DR.** Индекс — это отдельная структура, ускоряющая чтение и замедляющая запись. Выбор между B-tree и LSM определяет, что будет дешевле: читать или писать.

**Проблема.** Без индекса запрос читает всю таблицу — при миллионах строк это секунды и полная утилизация диска. С индексом на каждое поле запись замедляется в разы, а место удваивается. Между этими крайностями и находится проектирование.

**Как работает.**

*B-tree* — сбалансированное дерево, обновляемое **на месте**. Поиск за O(log n) с малой константой (высота дерева 3–4 уровня даже для миллиардов строк). Чтение эффективно и предсказуемо; запись требует изменения страниц и записи в журнал — при случайных ключах страдает локальность.

*LSM-дерево* (log-structured merge) — записи накапливаются в памяти (memtable), сбрасываются на диск последовательно (SSTable), периодически сливаются (compaction). Запись очень дешёвая и последовательная; чтение может потребовать просмотра нескольких уровней, что смягчается фильтрами Блума. Основа RocksDB, Cassandra, ScyllaDB, HBase; в PostgreSQL и MySQL — B-tree.

*Виды индексов, которые решают конкретные задачи:*
- **Составной** — порядок колонок критичен: индекс `(a, b)` обслуживает условия по `a` и по `a, b`, но не по одному `b` (правило левого префикса).
- **Покрывающий** — содержит все нужные запросу колонки, поэтому обращение к таблице не требуется (index-only scan).
- **Частичный** — только по строкам, удовлетворяющим условию: дешевле и меньше.
- **Специальные** — GIN/GiST для полнотекста и JSON, геоиндексы, хэш-индексы для точного равенства.

**Когда применять.** Индекс оправдан, если он покрывает частый запрос и обладает достаточной селективностью. **Когда нет:** индекс по полю с двумя значениями (флаг) бесполезен; индекс на таблице, которая пишется гораздо чаще, чем читается, — вреден.

**Альтернативы**

| Вариант | Плюс | Минус |
|---|---|---|
| B-tree | Предсказуемое чтение, диапазоны, сортировка | Дороже запись, фрагментация |
| LSM | Дешёвая запись, хорошее сжатие | Read/space amplification, паузы на compaction |
| Покрывающий индекс | Убирает обращение к таблице | Дублирование данных, дороже запись |
| Денормализация вместо индекса | Убирает соединение | Рассогласование ([DATA-03](#data-modeling)) |

**Trade-offs и режимы отказа.** Каждый индекс — это дополнительная запись при каждом INSERT/UPDATE. Индексы «на всякий случай» — типовая причина деградации записи. Планировщик может проигнорировать индекс при неверной статистике или низкой селективности. В LSM накопившийся долг compaction проявляется внезапно: ростом задержки чтения и всплеском ввода-вывода.

**Что мерить.** Доля index-only сканов, число прочитанных строк на возвращённую, размер индексов относительно таблицы, неиспользуемые индексы, глубина уровней и объём compaction в LSM.

## DATA-06 · SQL: порядок выполнения и оптимизация запросов

🎬 [#27](https://www.youtube.com/watch?v=BHwzDmr6d7s) · шаг [W3](../00-workflow.md#w3)

**TL;DR.** SQL пишется в одном порядке, а выполняется в другом. Понимание фактического порядка объясняет большинство «почему запрос медленный».

**Проблема.** Запрос читается сверху вниз начиная с SELECT, а выполняется начиная с FROM — из-за этого фильтр в HAVING вместо WHERE обрабатывает на порядки больше строк, а алиас из SELECT не виден в WHERE. Оптимизировать запрос, не понимая порядка, — угадывать.

**Как работает — логический порядок выполнения.**

`FROM / JOIN` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `DISTINCT` → `ORDER BY` → `LIMIT`

Отсюда следуют практические правила:
- **Фильтровать как можно раньше.** Условие в `WHERE` отсекает строки до группировки; в `HAVING` — после. `HAVING` нужен только для условий по агрегатам.
- **Сокращать объём до соединения.** Чем меньше строк входит в JOIN, тем дешевле он обходится.
- **`LIMIT` не спасает от сортировки** — чтобы вернуть 10 строк по `ORDER BY`, СУБД обязана упорядочить весь результат, если нет подходящего индекса.
- **Алиасы из `SELECT`** недоступны в `WHERE`, потому что `SELECT` вычисляется позже.

**Метод оптимизации.**
1. `EXPLAIN (ANALYZE, BUFFERS)` — смотреть фактические строки против оценочных: расхождение на порядки означает устаревшую статистику.
2. Найти самый дорогой узел плана: Seq Scan по большой таблице, Nested Loop с большим числом итераций, внешняя сортировка на диске.
3. Проверить, есть ли индекс, покрывающий условие ([DATA-05](#indexes)); проверить, не мешает ли функция над колонкой его использовать (`WHERE lower(email) = ...` не использует индекс по `email`).
4. Проверить типовые ошибки приложения: **N+1 запросов** ([PERF-06](11-performance-and-cost.md#pooling)), выборка всех колонок вместо нужных, пагинация по большому `OFFSET` ([NET-14](01-network-and-api.md#pagination)).

**Когда применять.** При любой деградации чтения — до того, как обсуждать кэш и реплики: неоптимальный запрос, размноженный кэшем, остаётся неоптимальным.

**Альтернативы**

| Вариант | Когда лучше | Цена |
|---|---|---|
| Индекс под запрос | Запрос частый и селективный | Замедление записи |
| Переписать запрос | План плох из-за формы запроса | Требует понимания плана |
| Материализованное представление | Тяжёлая агрегация, свежесть терпит | Стоимость и задержка пересчёта |
| Денормализация | Соединение неустранимо дорого | Рассогласование |
| Кэш | Один и тот же результат читают многие | Инвалидация ([CACHE-03](04-caching.md#cache-invalidation)) |

**Trade-offs и режимы отказа.** Оптимизация под один запрос ухудшает другие (лишние индексы). План меняется при изменении объёма данных — запрос, быстрый на тестовых 10 тысячах строк, может выбрать другой план на десяти миллионах. Хинты планировщику фиксируют решение, которое перестанет быть верным.

**Что мерить.** Время выполнения по перцентилям, число прочитанных страниц/буферов, доля Seq Scan по большим таблицам, самые дорогие запросы по суммарному времени (`pg_stat_statements`).

**Связано:** [DATA-05 индексы](#indexes) · [PERF-06 N+1 и пулы](11-performance-and-cost.md#pooling) · [NET-14 пагинация](01-network-and-api.md#pagination)

## DATA-07 · ACID и транзакции

🎬 [#60](https://www.youtube.com/watch?v=GAe5oB742dw) · шаг [W6](../00-workflow.md#w6)

**TL;DR.** Транзакция — способ не думать о частичном выполнении и о параллельных операциях. Из четырёх букв реальную работу делают A, I и D.

**Проблема.** Операция состоит из нескольких изменений: списать со счёта, зачислить на другой, записать в журнал. Сбой посередине оставляет данные в состоянии, которого не должно существовать. Параллельная операция, увидевшая промежуточное состояние, принимает решение на основе несуществующей реальности.

**Как работает.**
- **Atomicity** — всё или ничего. Реализуется журналом отмены: незавершённая транзакция откатывается. Правильнее читать как «abortability» — возможность безопасно прервать.
- **Consistency** — данные удовлетворяют инвариантам приложения. Это единственная буква, которую обеспечивает **не** база, а вы: БД проверит внешние ключи и ограничения, но «сумма остатков не меняется» — ваша ответственность.
- **Isolation** — параллельные транзакции ведут себя так, будто выполняются по очереди. На практике полная изоляция стоит дорого и почти всегда ослабляется ([DATA-08](#isolation)) — здесь прячется большинство сюрпризов.
- **Durability** — зафиксированное переживает отказ. Обеспечивается журналом (WAL) и fsync; в распределённой системе — подтверждением от реплик. Абсолютной durability не существует: сгоревший диск с несинхронизированным журналом теряет данные.

**Практические следствия.**
- Транзакция должна быть **короткой**: долгая держит блокировки и раздувает версии MVCC.
- Не выполнять внутри транзакции сетевые вызовы к другим сервисам — время удержания становится неконтролируемым.
- Границы транзакции = границы атомарности. Всё, что не поместилось внутрь, требует распределённого решения ([DIST-08](06-distributed-systems.md#distributed-transactions)).

**Альтернативы**

| Вариант | Когда лучше | Цена |
|---|---|---|
| Транзакция в одной БД | Данные в одном хранилище | Требует общих границ |
| Атомарность одного документа | Агрегат читается и пишется целиком | Нет операций между агрегатами |
| Saga с компенсациями | Несколько сервисов | Нет изоляции |
| Идемпотентная операция без транзакции | Один эффект, повтор безопасен | Нужен ключ идемпотентности |

**Trade-offs и режимы отказа.** BASE-хранилища меняют изоляцию и немедленную согласованность на доступность — это осознанный размен, а не «отсутствие транзакций». `synchronous_commit = off` ускоряет запись ценой потери последних транзакций при аварии. Транзакция, охватывающая слишком много, превращается в точку сериализации всей системы.

**Что мерить.** Длительность транзакций (p99), число откатов и дедлоков, возраст самой старой открытой транзакции, задержка fsync журнала.

**Связано:** [DATA-08 уровни изоляции](#isolation) · [DIST-08 распределённые транзакции](06-distributed-systems.md#distributed-transactions) · [DATA-09 репликация](#replication)

**Источники:** видео [#60](https://www.youtube.com/watch?v=GAe5oB742dw) · [Kleppmann, DDIA, гл. 7](https://dataintensive.net/) · [PostgreSQL — Reliability and the Write-Ahead Log](https://www.postgresql.org/docs/current/wal.html)

## DATA-08 · Уровни изоляции, аномалии, MVCC

➕ добавлено · шаг [W6](../00-workflow.md#w6)

**TL;DR.** «Транзакция есть» не значит «гонок нет». Уровень изоляции по умолчанию допускает аномалии, которые в бизнес-логике выглядят как потерянные деньги.

**Проблема.** Самый частый источник тихих багов: два процесса читают одно и то же, каждый принимает решение и записывает результат — итог не соответствует ни одному из сценариев по отдельности. Классика: два запроса проверили «остаток > 0» и оба списали; два администратора одновременно сняли себя с дежурства, оставив смену пустой.

**Аномалии и уровни**

| Аномалия | Что происходит | Предотвращается с уровня |
|---|---|---|
| Dirty read | Видны незафиксированные изменения | Read Committed |
| Non-repeatable read | Повторное чтение строки даёт другое значение | Repeatable Read / Snapshot |
| Phantom read | Повторный запрос по условию возвращает новые строки | Repeatable Read (в ряде СУБД) / Serializable |
| Lost update | Два «прочитал–изменил–записал» затирают друг друга | Repeatable Read с обнаружением, `SELECT FOR UPDATE`, atomic UPDATE |
| Write skew | Каждая транзакция видит корректное состояние, вместе нарушают инвариант | **Только Serializable** |

**Как работает MVCC.** Вместо блокировки читателей СУБД хранит несколько версий строки: транзакция видит снимок данных на момент своего начала. Читатели не блокируют писателей и наоборот — отсюда высокая параллельность. Плата: версии нужно вычищать (vacuum/purge), а долгая транзакция удерживает старые версии и раздувает хранилище.

**Что важно знать про конкретные СУБД.** В PostgreSQL уровень `repeatable read` реализован как snapshot isolation и **не** защищает от write skew — для этого нужен `serializable` (SSI, работает оптимистически и может отменить транзакцию с ошибкой сериализации, которую приложение обязано повторить). В MySQL InnoDB уровень по умолчанию `repeatable read` с блокировками next-key, что даёт другое поведение при тех же названиях. Одинаковые имена уровней в разных СУБД означают разные гарантии.

**Как выбирать защиту.**
- Инкремент/декремент → атомарный `UPDATE ... SET x = x - 1 WHERE x > 0` (без чтения в приложение).
- Обновление по прочитанным данным → **оптимистическая блокировка**: колонка версии и `WHERE version = ?`, повтор при нуле обновлённых строк.
- Инвариант между разными строками → `SERIALIZABLE` или явная блокировка, либо материализация конфликта (строка-замок).
- Уникальность → уникальный индекс; это самая надёжная и самая дешёвая проверка.

**Trade-offs и режимы отказа.** Serializable снижает пропускную способность и требует обработки ошибок сериализации — приложение обязано уметь повторять транзакцию. Пессимистические блокировки создают очередь и дедлоки. Оптимистические дешевле, но при высокой конкуренции вырождаются в бесконечные повторы.

**Что мерить.** Число дедлоков и ошибок сериализации, доля успешных повторов, длительность и возраст транзакций, рост «мусорных» версий.

**Связано:** [DATA-07 ACID](#acid) · [DIST-07 распределённые блокировки](06-distributed-systems.md#distributed-locks) · [CASE-08 бронирование](12-case-studies.md#booking)

## DATA-09 · Репликация

🎬 [#68](https://www.youtube.com/watch?v=_1IKwnbscQU) · шаг [W5](../00-workflow.md#w5)

**TL;DR.** Копии данных на нескольких узлах дают доступность и масштаб чтения; цена — отставание, которое видно пользователю.

**Проблема.** Одна копия данных означает: отказ узла = недоступность, а вся читающая нагрузка ложится на один сервер. Копии решают обе задачи и создают третью — расхождение между копиями.

**Как работает.**
- **Один лидер** (стандарт для реляционных БД). Запись только в лидера, реплики применяют его журнал. Простая модель, строгий порядок записи. Failover — выбор нового лидера ([DIST-05](06-distributed-systems.md#consensus)).
- **Синхронная репликация**: лидер подтверждает клиенту после записи на реплику. Нет потери данных, но задержка растёт, а отказ реплики блокирует запись. Компромисс — кворумная запись на одну из нескольких реплик.
- **Асинхронная**: подтверждение сразу, реплики догоняют. Быстро, но при отказе лидера последние транзакции теряются (RPO > 0).
- **Несколько лидеров** — запись в разных регионах; требует разрешения конфликтов ([DIST-10](06-distributed-systems.md#conflicts)).
- **Без лидера** — кворумы ([DIST-04](06-distributed-systems.md#quorum)).

**Лаг репликации — главный практический эффект.** Пользователь сохранил профиль, следующий запрос попал на отстающую реплику, изменения «исчезли». Лечится гарантиями сессии ([DIST-03](06-distributed-systems.md#consistency-models)): читать с лидера в течение нескольких секунд после записи, либо передавать номер версии и ждать, пока реплика догонит.

**Когда применять.** Реплики чтения — когда нагрузка читающая и запросы допускают отставание. **Когда нет:** реплики не масштабируют запись (каждая применяет весь поток изменений) и не защищают от логической ошибки ([REL-09](08-reliability.md#backup-dr)).

**Альтернативы**

| Вариант | Даёт | Не даёт |
|---|---|---|
| Реплики чтения | Масштаб чтения, резерв | Масштаб записи |
| Кэш | Ещё большее ускорение чтения | Транзакционность, сложность инвалидации |
| Шардирование | Масштаб записи и объёма | Простоту запросов |
| Бэкапы | Защиту от логической ошибки | Доступность |

**Trade-offs и режимы отказа.** Автоматический failover при неверном определении отказа даёт двух лидеров и расхождение (split-brain); поэтому переключение опирается на кворум. Реплика, отставшая надолго, при переключении теряет данные. Направление всей читающей нагрузки на реплики маскирует проблему до момента, когда лаг становится минутами.

**Что мерить.** Лаг репликации в секундах и в байтах, доля чтений с лидера, время failover, число откатов транзакций при переключении.

**Связано:** [DATA-10 шардирование](#sharding) · [DIST-03 модели согласованности](06-distributed-systems.md#consistency-models) · [REL-08 multi-region](08-reliability.md#multi-region) · [REL-09 бэкапы](08-reliability.md#backup-dr)

**Источники:** видео [#68](https://www.youtube.com/watch?v=_1IKwnbscQU) · [Kleppmann, DDIA, гл. 5](https://dataintensive.net/) · [PostgreSQL — High Availability, Load Balancing, and Replication](https://www.postgresql.org/docs/current/high-availability.html)

## DATA-10 · Шардирование и партиционирование

🎬 [#68](https://www.youtube.com/watch?v=_1IKwnbscQU) · шаг [W5](../00-workflow.md#w5)

**TL;DR.** Разрезание данных на части, живущие на разных узлах. Единственный способ масштабировать запись — и самое дорогое решение в дизайне данных.

**Проблема.** Одна нода упирается в потолок по записи, объёму или памяти под индексы. Реплики не помогают: они дублируют весь поток записи. Остаётся разделить данные — но выбранный ключ разделения определит, какие запросы останутся дешёвыми, а какие станут невозможными, и переиграть это позже почти нереально.

**Как работает.**
- **По хэшу ключа** — равномерное распределение, но диапазонные запросы требуют обхода всех шардов.
- **По диапазону** — эффективные диапазонные запросы, риск горячего шарда (последний диапазон принимает все новые записи).
- **По справочнику** — таблица соответствия «ключ → шард», максимальная гибкость, дополнительный компонент и точка отказа.
- **Геошардирование** — по региону пользователя; естественно ложится на multi-region.
- **Consistent hashing** ([DATA-11](#consistent-hashing)) — минимизирует переезд данных при изменении числа узлов.

**Выбор ключа — главное решение.** Хороший ключ: даёт равномерное распределение; присутствует в большинстве запросов (иначе они уходят во все шарды); группирует данные, которые читаются вместе (все заказы пользователя — в одном шарде). Типичный удачный выбор — идентификатор арендатора или пользователя.

**Что становится дорогим после шардирования.** Соединения между шардами. Транзакции, затрагивающие несколько шардов ([DIST-08](06-distributed-systems.md#distributed-transactions)). Глобально уникальные ограничения. Вторичные индексы: локальный индекс требует обхода всех шардов при поиске, глобальный — отдельной структуры со своей согласованностью. Агрегация по всем данным. Ребалансировка при добавлении узлов.

**Когда применять.** Когда исчерпаны вертикальный рост, кэш, реплики и асинхронность ([W5](../00-workflow.md#w5)) — и объём или запись действительно не помещаются. **Когда нет:** до этого момента; ранний шардинг — самая частая преждевременная оптимизация в дизайне данных.

**Альтернативы**

| Вариант | Когда лучше | Цена |
|---|---|---|
| Партиционирование внутри одной БД | Проблема в размере таблицы, а не в нагрузке | Не снимает нагрузку с узла |
| Вынос части данных в отдельное хранилище | Одна сущность доминирует по объёму | Два контура вместо одного |
| Архивирование холодных данных | Активна малая часть данных | Сложнее доступ к истории |
| Шардирование | Запись и объём не помещаются | Всё перечисленное выше |

**Trade-offs и режимы отказа.** Горячий шард сводит выигрыш к нулю: 90 % нагрузки на 10 % ключей — обычная ситуация (популярный пользователь, «текущий день»). Ребалансировка при работающей нагрузке — отдельный сложный процесс с двойной записью и переключением. Запросы без ключа шардирования становятся scatter-gather: их задержка определяется самым медленным шардом.

**Что мерить.** Распределение нагрузки и объёма по шардам (перекос), доля scatter-gather запросов, задержка кросс-шардовых операций, прогресс и влияние ребалансировки.

**Связано:** [DATA-11 consistent hashing](#consistent-hashing) · [DIST-09 уникальные ID](06-distributed-systems.md#unique-ids) · [DIST-08 распределённые транзакции](06-distributed-systems.md#distributed-transactions) · [DATA-18 мультитенантность](#multitenancy)

**Источники:** видео [#68](https://www.youtube.com/watch?v=_1IKwnbscQU) · [Kleppmann, DDIA, гл. 6](https://dataintensive.net/) · [Vitess — Sharding](https://vitess.io/docs/user-guides/configuration-advanced/sharding/) · [How Discord Stores Trillions of Messages](https://discord.com/blog/how-discord-stores-trillions-of-messages)

## DATA-11 · Consistent hashing

➕ добавлено · шаг [W5](../00-workflow.md#w5)

**TL;DR.** Способ распределить ключи по узлам так, чтобы при добавлении или потере узла переезжала малая доля данных, а не все.

**Проблема.** Наивное распределение `hash(key) mod N` работает, пока N постоянно. Стоит добавить или потерять узел — и **почти все** ключи меняют владельца: кэш обнуляется целиком, шарды требуют полной перетасовки. Для кэша это означает мгновенный шквал промахов и падение базы под ним.

**Как работает.**
- Узлы и ключи отображаются на общее кольцо значений хэша. Ключ принадлежит первому узлу по часовой стрелке.
- При удалении узла его ключи переходят только к соседу; при добавлении — забирает часть у соседа. Переезжает примерно `K/N` ключей вместо всех.
- **Виртуальные узлы**: каждый физический узел представлен десятками-сотнями точек на кольце. Это выравнивает распределение (иначе разброс велик) и позволяет учитывать разную мощность машин — сильному узлу дают больше точек.
- Репликация: копии кладутся на следующие N узлов по кольцу.

**Когда применять.** Распределённые кэши (клиенты memcached), Dynamo-подобные хранилища (Cassandra, Riak), распределение партиций между потребителями. **Когда нет:** если состав узлов стабилен и переезд данных допустим, обычный хэш проще; для L7-балансировки запросов чаще достаточно round-robin или least-connections ([EDGE-01](02-traffic-and-edge.md#load-balancing)).

**Альтернативы**

| Вариант | Плюс | Минус |
|---|---|---|
| `hash mod N` | Простота | Полная перетасовка при изменении N |
| Consistent hashing + vnodes | Минимальный переезд, учёт весов | Метаданные кольца, сложнее отладка |
| Rendezvous (HRW) hashing | Проще, без кольца, естественные веса | Стоимость O(N) на ключ |
| Jump consistent hash | Очень быстрый, без памяти | Не поддерживает произвольное удаление узлов |
| Maglev | Равномерность + скорость, для балансировщиков | Сложнее реализация |

**Trade-offs и режимы отказа.** Без виртуальных узлов распределение получается неравномерным, и отдельные узлы получают кратно больше данных. Горячий ключ consistent hashing не лечит — он распределяет ключи, а не нагрузку на один ключ ([CACHE-04](04-caching.md#cache-pathologies)). При изменении состава кольца часть запросов какое-то время идёт к «неправильному» узлу — для кэша это промахи, для хранилища требует передачи данных.

**Что мерить.** Перекос распределения ключей по узлам, доля ключей, сменивших владельца при изменении состава, всплеск промахов кэша после ребалансировки.

**Связано:** [DATA-10 шардирование](#sharding) · [CACHE-05 Redis](04-caching.md#redis) · [DIST-04 кворумы](06-distributed-systems.md#quorum)

**Источники:** [Karger et al. — Consistent Hashing and Random Trees (1997)](https://dl.acm.org/doi/10.1145/258533.258660) · [Dynamo paper (SOSP 2007)](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf) · [Google — Maglev (NSDI 2016)](https://research.google/pubs/pub44824/)

## DATA-12 · Object storage и работа с файлами

➕ добавлено · шаг [W3](../00-workflow.md#w3)

**TL;DR.** Файлы хранят в объектном хранилище, а в базе — только ссылку и метаданные. Загрузка и отдача идут мимо приложения.

**Проблема.** Картинки, видео, документы и экспорты не помещаются в модель реляционной БД: они раздувают её объём, ломают бэкапы, а отдача файла через приложение занимает поток на всё время передачи. Загрузка стомегабайтного файла через собственный сервис — это прокачка трафика дважды и таймауты на медленных сетях.

**Как работает.**
- **Объектное хранилище** (S3, GCS, MinIO) — плоское пространство ключей, HTTP-доступ, практически неограниченный объём, оплата по факту. Объект неизменяем: «изменение» — это перезапись целиком.
- **Presigned URL** — приложение выдаёт клиенту временную подписанную ссылку, и браузер загружает файл **напрямую** в хранилище. Сервис не видит байтов, не тратит трафик и потоки; права и срок жизни зашиты в подпись.
- **Multipart upload** — большой файл режется на части, части грузятся параллельно и повторяются независимо при сбое.
- **CDN перед хранилищем** ([EDGE-05](02-traffic-and-edge.md#cdn)) — отдача из ближайшей точки присутствия.
- **Классы хранения и lifecycle** — автоматический перевод редко используемых объектов в холодные классы и удаление по возрасту ([DATA-19](#retention)).
- **Схема данных:** в БД лежат ключ объекта, размер, тип, контрольная сумма, статус (`ожидает загрузки` → `готов`) и владелец. Загрузка подтверждается отдельным вызовом или событием хранилища.

**Когда применять.** Для любых бинарных данных пользователя. **Когда нет:** для мелких часто изменяемых значений (настройки, флаги) — там дешевле БД или кэш; для данных, по содержимому которых нужен запрос.

**Альтернативы**

| Вариант | Когда лучше | Цена |
|---|---|---|
| Object storage + presigned URL | Стандартный случай | Нужна обработка «осиротевших» объектов |
| BLOB в реляционной БД | Мелкие файлы, нужна транзакционность со строкой | Раздувание БД и бэкапов |
| Файловая система / NFS | Legacy, специфичные требования | Масштабирование и отказоустойчивость на вас |
| Проксирование через приложение | Нужен контроль каждого байта (антивирус, водяной знак) | Трафик и потоки приложения |

**Trade-offs и режимы отказа.** Прямая загрузка от клиента требует проверки типа и размера **после** факта, а также ограничения по подписи — иначе хранилище превращается в бесплатный файлообменник. Ссылка на объект и запись в БД не атомарны: нужен либо статус, либо сборщик мусора для незавершённых загрузок. Удаление объекта, на который ещё ссылается кэш или CDN, даёт битые ссылки.

**Что мерить.** Доля незавершённых загрузок, объём «осиротевших» объектов, стоимость по классам хранения, доля отдачи через CDN против прямых обращений.

**Связано:** [EDGE-05 CDN](02-traffic-and-edge.md#cdn) · [DATA-19 retention](#retention) · [CASE-07 загрузка видео](12-case-studies.md#video)

**Источники:** [AWS S3 — Presigned URLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html) · [AWS S3 — Multipart upload](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html) · [AWS S3 — Consistency model](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel)

## DATA-13 · Полнотекстовый поиск и инвертированный индекс

🎬 [#76](https://www.youtube.com/watch?v=TByRaraQqW4) · шаг [W3](../00-workflow.md#w3)

**TL;DR.** Поиск по тексту требует отдельной структуры — инвертированного индекса — и отдельного хранилища, которое почти никогда не должно быть источником истины.

**Проблема.** `LIKE '%слово%'` не использует индекс и читает всю таблицу. Кроме того, пользователю нужен не точный подстрочный поиск, а морфология, опечатки, синонимы и ранжирование по релевантности — задача принципиально другого класса, чем выборка по ключу.

**Как работает.**
- **Инвертированный индекс** — отображение «терм → список документов, где он встречается» (posting list) с позициями. Поиск по нескольким словам — пересечение списков.
- **Анализ текста** — токенизация, приведение к нижнему регистру, отбрасывание стоп-слов, нормализация словоформ (стемминг/лемматизация), n-граммы для опечаток и автодополнения. Одинаковый анализатор обязан применяться и при индексации, и при запросе.
- **Ранжирование** — BM25 как современный стандарт (развитие TF-IDF): чем реже терм в коллекции и чаще в документе, тем выше вклад, с поправкой на длину документа. Поверх накладываются бизнес-факторы: свежесть, популярность, персонализация.
- **Near-real-time.** Документ становится видимым не мгновенно, а после обновления сегмента (в Elasticsearch — секунда по умолчанию). Это архитектурное свойство, а не настройка производительности.
- **Модель данных денормализована**: документ содержит всё нужное для выдачи, потому что соединений нет.
- **Векторный/гибридный поиск** — эмбеддинги и ANN-индексы для семантического сходства, обычно в комбинации с BM25.

**Когда применять.** Полнотекстовый поиск, фасеты, автодополнение, поиск по логам. Для умеренных объёмов встроенных возможностей PostgreSQL (`tsvector` + GIN) достаточно, и это дешевле, чем отдельный кластер. **Когда нет:** поисковый движок — не БД: он не даёт транзакций и надёжной durability, поэтому источником истины остаётся основное хранилище.

**Альтернативы**

| Вариант | Когда лучше | Цена |
|---|---|---|
| Полнотекстовый поиск в PostgreSQL | Объёмы умеренные, не хочется второго хранилища | Меньше возможностей ранжирования и масштаба |
| Elasticsearch / OpenSearch | Большие объёмы, фасеты, аналитика по логам | Отдельный кластер и его эксплуатация |
| Внешний поисковый сервис | Не хочется эксплуатировать | Стоимость, зависимость |
| Векторный поиск | Нужна семантика, а не совпадение слов | Стоимость эмбеддингов, качество зависит от модели |

**Trade-offs и режимы отказа.** Индекс — производная структура: он расходится с источником истины при сбое конвейера, поэтому нужны переиндексация и сверка. Переиндексация большого корпуса — часы, её планируют заранее (обычно через индексацию в новый индекс и переключение алиаса). Изменение анализатора требует полной переиндексации.

**Что мерить.** Отставание индексации, доля запросов без результатов, задержка поиска по перцентилям, метрики качества (CTR по позициям, доля переформулировок запроса).

**Связано:** [DATA-15 OLTP/OLAP](#oltp-olap) · [MSG-07 CDC](05-async-and-messaging.md#outbox) · [CASE-06 автодополнение](12-case-studies.md#autocomplete)

**Источники:** видео [#76](https://www.youtube.com/watch?v=TByRaraQqW4) · [Elasticsearch — Inverted index](https://www.elastic.co/guide/en/elasticsearch/reference/current/documents-indices.html) · [PostgreSQL — Full Text Search](https://www.postgresql.org/docs/current/textsearch.html) · [Introduction to Information Retrieval (Manning et al.)](https://nlp.stanford.edu/IR-book/)

## DATA-14 · Геоданные и геоиндексы

➕ добавлено · шаг [W3](../00-workflow.md#w3)

**TL;DR.** «Найти ближайшие объекты в радиусе» — запрос, который обычный индекс не обслуживает. Пространство сводят к одномерному ключу (геохэш, ячейки) либо используют пространственный индекс.

**Проблема.** Два независимых индекса по широте и долготе почти бесполезны: каждый отбирает полосу через всю карту, а пересечение полос всё равно приходится проверять построчно. Вычисление расстояния для всех строк — полный скан. При этом запрос «двадцать ближайших» — основа целого класса продуктов: доставка, такси, карты, поиск по близости.

**Подходы.**
- **Геохэш.** Биты широты и долготы перемежаются, результат кодируется строкой: общий префикс означает соседство. Ключ получается одномерным и сортируемым, поэтому работает в любой БД и в упорядоченных множествах Redis. Главная тонкость — **граничный эффект**: два близких объекта по разные стороны границы ячейки имеют разные префиксы, поэтому запрос обязан проверять соседние ячейки, а не только свою.
- **Ячеистые сетки: S2 и H3.** S2 проецирует сферу на кубы и нумерует ячейки кривой Гильберта, сохраняющей локальность. H3 использует гексагональную сетку: у гексагона все шесть соседей равноудалены, что делает агрегацию и сглаживание корректнее, чем на квадратах. Обе схемы дают уровни детализации и удобны как ключ для агрегатов и для шардирования.
- **Пространственный индекс (R-дерево).** Хранит ограничивающие прямоугольники; в отличие от хэшей, работает не только с точками, но и с линиями и полигонами: «внутри района», «пересекает маршрут». Это путь PostGIS.
- **Двухфазный запрос.** Практически всегда: сначала грубый отбор кандидатов по ячейке или прямоугольнику, затем точное вычисление расстояния и сортировка по небольшому набору.

**Что важно помнить.** Расстояние по прямой на сфере (гаверсинус) — приближение; для точности нужен эллипсоид, для практики обычно достаточно первого. Расстояние по прямой и по дорогам различаются в разы — «ближайший» по воздуху может быть на другом берегу реки; за маршруты отвечает отдельный сервис. Координаты имеют систему отсчёта, и смешение систем даёт ошибки в сотни метров.

**Альтернативы**

| Вариант | Когда лучше | Цена |
|---|---|---|
| Геохэш в обычной БД или Redis | Точки, простой поиск по близости | Граничные ячейки, только точки |
| H3 / S2 как ключ ячейки | Агрегация по территории, шардирование | Своя библиотека, дискретность уровней |
| PostGIS (R-дерево) | Полигоны, пересечения, сложная геометрия | Расширение и его эксплуатация |
| Специализированный геосервис | Маршруты, пробки, изохроны | Внешняя зависимость |

**Trade-offs и режимы отказа.** Размер ячейки — компромисс: мелкая даёт точность и много ячеек для проверки, крупная — мало кандидатов, но грубый отбор. Плотные районы создают горячие ячейки: в центре города в одну ячейку попадает столько же объектов, сколько в целую область на периферии — при шардировании по ячейке это перекос ([DATA-10](#sharding)). Движущиеся объекты меняют позицию чаще, чем их читают: для них уместнее хранилище в памяти с коротким временем жизни, а не индекс в основной БД.

**Что мерить.** Задержка поиска ближайших по перцентилям, число проверенных кандидатов на один результат (эффективность грубого отбора), распределение объектов по ячейкам, частота обновления позиций.

**Связано:** [DATA-10 шардирование](#sharding) · [CACHE-05 Redis](04-caching.md#redis) · [CASE-10 геопоиск ближайших объектов](12-case-studies.md#geo-search)

**Источники:** [PostGIS — Spatial indexing](https://postgis.net/workshops/postgis-intro/indexing.html) · [Uber H3 — Hexagonal hierarchical spatial index](https://www.uber.com/en-DE/blog/h3/) · [Google S2 Geometry](https://s2geometry.io/) · [Redis — Geospatial indexes](https://redis.io/docs/latest/develop/data-types/geospatial/)

<a id="oltp-olap"></a>

## DATA-15 · OLTP vs OLAP: warehouse, lake, lakehouse

🎬 [#101](https://www.youtube.com/watch?v=taSmwcqdkQk), [#66](https://www.youtube.com/watch?v=kGT4PcTEPP8) · шаг [W3](../00-workflow.md#w3)

**TL;DR.** Транзакционная и аналитическая нагрузки требуют разного физического устройства данных. Их разделение — не роскошь, а условие стабильности боевой системы.

**Проблема.** Аналитический запрос читает миллионы строк и держит ресурсы минутами. Выполненный на боевой БД, он вытесняет полезные данные из буферного пула, удерживает старые версии строк и деградирует пользовательские запросы. Отдельная реплика «для аналитиков» помогает лишь частично: строковое хранение всё равно неэффективно для агрегаций по нескольким колонкам из сотни.

**Как работает.**
- **OLTP** — много коротких операций, точечные чтения и записи по ключу, строковое хранение, индексы под селективные запросы.
- **OLAP** — мало запросов, каждый сканирует и агрегирует огромные объёмы. **Колоночное хранение**: значения одной колонки лежат подряд, поэтому читается только нужное, а однородные данные сжимаются в разы. Отсюда порядковая разница в скорости агрегаций.
- **Data warehouse** — структурированное аналитическое хранилище со схемой (Snowflake, BigQuery, Redshift, ClickHouse). Схема при записи, высокое качество данных.
- **Data lake** — сырые файлы в объектном хранилище (обычно Parquet). Схема при чтении, дёшево, но легко превращается в «болото» без каталога и контроля качества.
- **Lakehouse** — табличный формат поверх файлов озера (Iceberg, Delta Lake, Hudi), дающий транзакции, эволюцию схемы и путешествие во времени. Совмещает дешёвое хранение с гарантиями склада.
- **Доставка данных**: batch ETL/ELT по расписанию или потоковый CDC ([MSG-07](05-async-and-messaging.md#outbox)) для near-real-time.

**Когда применять.** Разделять контуры, как только аналитика начинает влиять на боевую нагрузку или требовать данных из нескольких систем. **Когда нет:** пока отчётов мало и они лёгкие, отдельная реплика проще и дешевле полноценного склада.

**Альтернативы**

| Вариант | Когда лучше | Цена |
|---|---|---|
| Отчёты на реплике OLTP | Малые объёмы, простые отчёты | Не масштабируется, строковое хранение |
| Колоночная БД (ClickHouse) | Быстрая аналитика на своих данных | Отдельная система, ограничения обновлений |
| Облачный warehouse | Не хочется эксплуатировать | Стоимость запросов растёт с аппетитом аналитиков |
| Lakehouse | Много сырых данных, нужны и SQL, и ML | Сложность стека и каталога |

**Trade-offs и режимы отказа.** Дублирование данных требует контроля соответствия: расхождение витрины и источника подрывает доверие ко всей аналитике. Пайплайн — такая же боевая система: его отказ обнаруживается по пустому дашборду через сутки, если нет мониторинга свежести. Данные в озере без каталога и владельца быстро перестают быть используемыми.

**Что мерить.** Свежесть витрин (лаг от источника), успешность и длительность пайплайнов, сверка контрольных сумм и количеств строк, стоимость запросов.

**Связано:** [MSG-11 data pipeline](05-async-and-messaging.md#pipeline) · [MSG-07 CDC](05-async-and-messaging.md#outbox) · [DATA-01 выбор хранилища](#storage-choice)

**Источники:** видео [#101](https://www.youtube.com/watch?v=taSmwcqdkQk), [#66](https://www.youtube.com/watch?v=kGT4PcTEPP8) · [Kleppmann, DDIA, гл. 3, раздел про аналитику](https://dataintensive.net/) · [Apache Iceberg — Table format spec](https://iceberg.apache.org/spec/) · [Databricks — Lakehouse (CIDR 2021)](https://www.cidrdb.org/cidr2021/papers/cidr2021_paper17.pdf)

<a id="data-integrity"></a>

## DATA-16 · Целостность и сверка данных

➕ добавлено · шаг [W9](../00-workflow.md#w9)

**TL;DR.** Отказ виден сразу, порча данных — нет. Нужен отдельный механизм, который регулярно проверяет инварианты и сравнивает копии, иначе расхождение обнаружит клиент.

**Проблема.** Система работает, метрики зелёные, ошибок нет — а цифры неверны. Источники расхождений: производная копия отстала или потеряла событие (кэш, поисковый индекс, витрина); распределённая операция оборвалась на середине и компенсация не выполнилась ([DIST-08](06-distributed-systems.md#distributed-transactions)); гонка или баг записали несогласованное состояние; миграция обработала часть строк ([DATA-17](#migrations)). Общая черта — **тишина**: без специальной проверки такое не обнаруживается неделями, а к моменту обнаружения историю уже нельзя пересчитать.

**Эшелоны защиты.**

1. **Ограничения в самой БД** — самый дешёвый и надёжный уровень: `NOT NULL`, внешние ключи, `CHECK`, уникальные индексы. Их регулярно отключают «ради производительности» и почти всегда об этом жалеют: приложение гарантирует инвариант только пока в нём нет багов и пока оно одно.
2. **Инварианты как проверяемые утверждения.** «Сумма проводок по счёту равна балансу», «у каждого оплаченного заказа есть платёж», «у каждой позиции есть склад». Формулируются как запросы и выполняются по расписанию отдельным процессом. Ненулевой результат — это находка, на которую заведён алерт.
3. **Сверка копий** (reconciliation). Периодическое сравнение источника и производной: по количеству записей, по контрольным суммам блоков, по агрегатам за период. Сравнение делается на срезе с учётом лага репликации, иначе ложные расхождения забьют сигнал.
4. **Проверки на уровне хранения.** Контрольные суммы страниц ловят порчу на диске; восстановление бэкапа с прогоном проверок — единственное доказательство, что бэкап рабочий ([REL-09](08-reliability.md#backup-dr)).
5. **Устранение классов расхождений на входе:** идемпотентность ([NET-16](01-network-and-api.md#idempotency)) убирает дубликаты, outbox ([MSG-07](05-async-and-messaging.md#outbox)) — потерянные события. Сверка ловит остаток.
6. **Журнал изменений** для расследования: без истории «кто и когда поменял» причину расхождения установить нельзя ([SEC-12](09-security.md#audit)).

**Седьмой случай — арбитр вне системы.** Все шесть эшелонов выше сверяют систему с самой собой: копию с источником, агрегат с проводками, страницу с контрольной суммой. Но источником истины бывает физический мир — товар на полке, остаток на складе, документ у контрагента, — и тогда **ни один эшелон не применим**: спросить арбитра стоит человеко-часов, а не запроса.

Меняется сам вопрос: не «как сверять», а **«как часто мы имеем право спрашивать»**. Спросить арбитра стоит человеко-часов, и частота сверки становится **параметром решения, а не свойством механизма**: во что обходится нужная точность и кто за это платит, решается за пределами карточки. Отсюда три следствия.

- **Сплошная сверка — не измеритель, а калибровка.** Она редка и точна; выборка часта и смещена. Без сплошной смещение выборки неизвестно, без выборки между сплошными не видно ничего.
- **Расхождение, не оставляющее следа в данных, выборкой ловится, потоком — нет.** Журнал операций фиксирует отсканированное; переставленная молча коробка следа не оставляет по построению. Поток ловит **противоречия** (выдача без приёмки, две выдачи одной единицы) и объясняет расхождение, когда оно найдено, — но не находит его.
- **Цена измерения входит в цену обещания**, а не в накладные расходы: см. форму «корректность» в [D-10](../decisions/D-10-service-level-objectives.md).

**Что делать с найденным.** Автоматически исправлять можно только там, где источник истины однозначен — например, перестроить производную из источника. Расхождение между двумя равноправными записями исправляется человеком, а автоисправление без разбора причины маскирует баг: цифры сходятся, ошибка продолжает работать.

**Когда применять.** Обязательно — деньги, остатки, права доступа, счётчики, любая производная копия. **Когда нет:** для данных, которые дешевле перестроить целиком, чем сверять (кэш с коротким временем жизни).

**Trade-offs и режимы отказа.** Сверка — это дополнительная нагрузка, часто тяжёлая: полное сравнение больших таблиц выполняют по частям и в непиковое время. Слишком чувствительные пороги дают ложные срабатывания из-за лага, и на них перестают реагировать. Сверка сама может быть неверной — тогда доверие подрывается сильнее, чем при её отсутствии, поэтому её логику проверяют так же, как боевой код.

**Что мерить.** Доля расхождений на прогон, время от возникновения до обнаружения, число нарушенных инвариантов по типам, возраст самой старой незавершённой распределённой операции, доля автоматически исправленных расхождений против ручных.

**Связано:** [DATA-17 миграции](#migrations) · [MSG-07 outbox и CDC](05-async-and-messaging.md#outbox) · [DIST-08 распределённые транзакции](06-distributed-systems.md#distributed-transactions) · [REL-09 бэкапы и DR](08-reliability.md#backup-dr)

**Источники:** седьмой случай и его следствия — разбор прогона [E-03 · ADR-0005](../examples/E-03-pickup/ADR-0005-objectives.md), где внешним арбитром была ручная инвентаризация · [Google SRE Book, гл. 26 «Data Integrity»](https://sre.google/sre-book/data-integrity/) · [Kleppmann, DDIA, гл. 12 — аудит и сквозная проверка](https://dataintensive.net/) · [PostgreSQL — Data checksums](https://www.postgresql.org/docs/current/checksums.html)

## DATA-17 · Миграции схемы без простоя

➕ добавлено · шаг [W9](../00-workflow.md#w9)

**TL;DR.** Схема меняется чаще архитектуры. Безопасная миграция — это последовательность обратно совместимых шагов, а не одно изменение.

**Проблема.** Во время выката одновременно работают старая и новая версии кода. Изменение, ломающее старую версию (удаление колонки, переименование, ужесточение ограничения), гарантированно вызывает ошибки — либо во время выката, либо при откате. Плюс сама операция может заблокировать таблицу: `ALTER TABLE` с перезаписью на большой таблице — это минуты недоступности.

**Как работает — паттерн expand → migrate → contract.**
1. **Expand.** Добавить новое, ничего не ломая: новая колонка (nullable, без обязательного значения), новая таблица, новый индекс — **конкурентно**, без долгой блокировки.
2. **Двойная запись.** Новая версия кода пишет и в старое, и в новое место; читает пока из старого.
3. **Backfill.** Перенести исторические данные **партиями** с паузами, отслеживая нагрузку и лаг репликации. Backfill должен быть возобновляемым и идемпотентным.
4. **Переключение чтения** на новое место — желательно под фича-флагом, чтобы откат был мгновенным ([REL-04](08-reliability.md#degradation)).
5. **Contract.** Убрать двойную запись и удалить старое — отдельным релизом, через недели, когда откат уже точно не понадобится.

Переименование колонки выполняется как «добавить новую → скопировать → переключить → удалить старую», а не одной командой.

**Опасные операции.** Добавление NOT NULL со значением по умолчанию, изменение типа, добавление внешнего ключа и уникального индекса — в разных СУБД и версиях они по-разному блокируют таблицу. Проверять поведение нужно для своей версии; для MySQL часто применяют онлайн-инструменты (gh-ost, pt-online-schema-change), в PostgreSQL — `CREATE INDEX CONCURRENTLY` и добавление ограничений в режиме `NOT VALID` с последующей валидацией.

**Когда применять.** Для любой схемы в системе, которая не может позволить себе окно простоя. **Когда нет:** если окно допустимо и данных мало, простая миграция дешевле по трудозатратам.

**Альтернативы**

| Вариант | Когда лучше | Цена |
|---|---|---|
| Expand/contract | Стандарт для боевых систем | Несколько релизов, дисциплина |
| Окно простоя | Малая система, ночь выходного | Недоступность |
| Теневая таблица + переключение | Радикальная перестройка | Двойной объём, сложное переключение |
| Версионирование в самих данных (schema-on-read) | Документные хранилища | Логика совместимости в коде навсегда |

**Trade-offs и режимы отказа.** Backfill без ограничения скорости кладёт базу или разгоняет лаг репликации до минут. Двойная запись без транзакционной гарантии расходится — нужна сверка. Забытый шаг contract оставляет систему в переходном состоянии на годы: это самый частый исход, поэтому его планируют сразу с датой.

**Что мерить.** Длительность блокировок при DDL, прогресс и скорость backfill, лаг репликации во время миграции, расхождение между старым и новым представлением данных.

**Связано:** [NET-17 версионирование API](01-network-and-api.md#versioning) · [OPS-02 стратегии деплоя](10-delivery-and-ops.md#deploy) · [REL-04 фича-флаги](08-reliability.md#degradation)

**Источники:** [Martin Fowler — Evolutionary Database Design](https://martinfowler.com/articles/evodb.html) · [PostgreSQL — ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html) · [gh-ost — online schema migration for MySQL](https://github.com/github/gh-ost)

<a id="multitenancy"></a>

## DATA-18 · Мультитенантность

➕ добавлено · шаг [W3](../00-workflow.md#w3)

**TL;DR.** Три модели изоляции данных арендаторов: общая таблица, отдельная схема, отдельная база. Выбор определяется требованиями к изоляции и числом арендаторов.

**Проблема.** В B2B-системе данные разных организаций не должны пересекаться — ни по ошибке в запросе, ни по нагрузке. Одновременно нужно обслуживать и тысячи мелких арендаторов, и нескольких крупных, для которых обещана изоляция производительности и, возможно, хранение в своей юрисдикции.

**Как работает.**

| Модель | Изоляция | Масштаб по числу арендаторов | Сложность эксплуатации |
|---|---|---|---|
| Общая таблица с `tenant_id` | Слабая (только код и политики) | Десятки тысяч | Низкая: одна миграция на всех |
| Схема на арендатора | Средняя | Сотни–тысячи | Средняя: миграция на каждую схему |
| База на арендатора | Сильная | Десятки–сотни | Высокая: N бэкапов, N обновлений |
| Гибрид: пул для мелких, выделенное для крупных | Настраиваемая | Практичный компромисс | Две ветки логики |

**Обязательные механики для общей таблицы.**
- `tenant_id` в **каждой** таблице и в **каждом** индексе первым полем — это одновременно и изоляция, и естественный ключ шардирования ([DATA-10](#sharding)).
- Принудительная фильтрация на уровне БД (row-level security) или единой прослойки доступа — полагаться на дисциплину разработчиков нельзя: один забытый `WHERE` = утечка между арендаторами.
- Квоты и ограничения на арендатора ([EDGE-06](02-traffic-and-edge.md#rate-limiting)) — от шумного соседа.
- `tenant_id` в логах, метриках и трассировках, иначе диагностика инцидента у одного клиента невозможна.

**Когда применять.** Общая таблица — по умолчанию для SaaS. Выделенная база — под требования регуляторов, крупных клиентов и для изоляции нагрузки. **Когда нет:** для одного крупного внутреннего заказчика мультитенантность не нужна.

**Trade-offs и режимы отказа.** Общая модель делает любую ошибку фильтрации инцидентом безопасности. Выделенные базы превращают миграцию в распределённую операцию над сотнями экземпляров с частичными отказами. Крупный арендатор в общем пуле создаёт перекос ([DATA-10](#sharding)) и «шумного соседа». Экспорт и удаление данных одного арендатора в общей модели — отдельная работа, которую закладывают заранее ([DATA-19](#retention)).

**Что мерить.** Распределение объёма и нагрузки по арендаторам, число запросов без фильтра по арендатору (должно быть нулевым), задержка по крупнейшим арендаторам отдельно от медианы, успешность миграций по всем экземплярам.

## DATA-19 · Retention, удаление данных, приватность

➕ добавлено · шаг [W0](../00-workflow.md#w0)

**TL;DR.** Сколько хранить и как удалять — это требование, влияющее на схему, бэкапы и стоимость. Его формулируют на входе, а не когда придёт запрос на удаление.

**Проблема.** Данные копятся бесконечно: они дёшевы поштучно и дороги в сумме — растёт стоимость, замедляются запросы, раздуваются бэкапы. Одновременно закон и договор требуют уметь **удалить** данные человека, а копии к тому моменту разъехались по репликам, кэшам, поисковому индексу, аналитическому складу, логам и бэкапам.

**Как работает.**
- **Политика хранения по классам данных**: операционные (месяцы), финансовые (годы по закону), логи (недели), аналитические агрегаты (бессрочно, но обезличенно).
- **Механика удаления**: партиционирование по времени и **удаление партиции целиком** вместо `DELETE` построчно — на порядки дешевле; TTL в хранилищах, которые его поддерживают; lifecycle-правила в объектном хранилище.
- **Мягкое против жёсткого удаления.** Мягкое (`deleted_at`) удобно для отмены и аудита, но это не удаление с точки зрения приватности и не освобождает место. Обычно нужны оба: мягкое сразу, жёсткое по расписанию.
- **Карта распространения данных.** Для каждого класса персональных данных — список всех мест, где он оказывается. Без неё удаление всегда неполное.
- **Крипто-шреддинг** для бэкапов: данные шифруются ключом, привязанным к субъекту; удаление ключа делает данные невосстановимыми, не требуя переписывать архивы.
- **Обезличивание** вместо удаления там, где нужна историческая аналитика: агрегаты сохраняются, идентификаторы отсекаются.

**Когда применять.** Всегда, когда система хранит данные людей. Формулировать на шаге [W0](../00-workflow.md#w0) вместе с остальными требованиями.

**Альтернативы**

| Вариант | Когда лучше | Цена |
|---|---|---|
| Партиции по времени + drop | Данные естественно стареют | Схема должна это предусматривать |
| TTL в хранилище | Поддерживается движком | Нет контроля момента удаления |
| Мягкое удаление | Нужны отмена и аудит | Не освобождает место, не закрывает приватность |
| Крипто-шреддинг | Нужно «удаление» в бэкапах | Управление ключами на субъект |
| Архивирование в холодное хранилище | Данные нужны редко, но нужны | Медленный доступ |

**Trade-offs и режимы отказа.** Требование удалить конфликтует с требованием хранить (финансовые записи) — разрешается разделением данных на классы, а не одним решением. Бэкапы — самое частое место, где «удалённые» данные продолжают жить. Массовое `DELETE` без партиционирования создаёт долгую транзакцию, раздувает версии и роняет производительность.

**Что мерить.** Объём по классам данных и его рост, возраст самых старых записей относительно политики, время выполнения запроса на удаление, доля мест из карты распространения, где удаление подтверждено.
